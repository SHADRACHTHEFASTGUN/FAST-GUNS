2. SECURITY ARCHITECTURE
====================================================================

The architecture MUST follow a LOCAL-FIRST / PEER-TO-PEER model.

Message content must never be stored on a central backend.

Preferred architecture:

CLIENT
    |
    +-- Local encrypted identity vault
    |
    +-- Local encrypted message database
    |
    +-- WebCrypto / mature cryptographic library
    |
    +-- WebRTC DataChannel
    |
    +-- Minimal signaling / rendezvous mechanism
    |
    +-- Optional STUN/TURN infrastructure
    |
    +-- Remote peer

IMPORTANT:

WebRTC requires signaling.

Therefore do NOT falsely advertise:

"100% backend-free"

if signaling infrastructure is required.

Instead architect the system so that:

- signaling knows nothing about plaintext messages
- signaling does not receive encryption keys
- signaling does not receive message bodies
- signaling cannot decrypt conversations
- signaling does not store conversations
- signaling only assists peers in finding each other / negotiating
  connections
- WebRTC carries the encrypted application payload

If technically possible, make signaling ephemeral.

Use short-lived signaling state.

Delete signaling state after connection establishment.

Do not build a permanent message database.

====================================================================
3. END-TO-END ENCRYPTION
====================================================================

This is the most important component.

Use established cryptographic standards.

DO NOT invent cryptography.

The implementation should use a mature cryptographic library or
well-reviewed browser-compatible primitives.

Preferred direction:

WebCrypto API for browser-native primitives where appropriate.

Use modern authenticated encryption such as:

AES-256-GCM

or another well-established AEAD construction supported by the
chosen cryptographic architecture.

Use modern public-key cryptography for identity and key agreement.

Where appropriate, use:

X25519

Ed25519

HKDF

SHA-256 / SHA-512

AES-256-GCM

or a mature protocol/library providing equivalent modern primitives.

DO NOT simply implement a homemade "AES + RSA" chat protocol.

DO NOT use insecure ECB mode.

DO NOT reuse nonces.

DO NOT derive keys using raw passwords directly.

Use a proper password-based key derivation function for local vault
protection, such as Argon2id where available through a trustworthy
implementation.

Use strong random values from:

crypto.getRandomValues()

or equivalent secure randomness.

====================================================================

IndexedDB

All stored message records must be encrypted.

Example conceptual structure:

    conversationId: encrypted,

    timestamp: encrypted,
    ciphertext: encrypted,

Encrypt sensitive values before writing them.

The encryption key must not simply be stored beside the ciphertext.
