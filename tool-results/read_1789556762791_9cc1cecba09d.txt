   180→2. SECURITY ARCHITECTURE
   181→====================================================================
   182→
   183→The architecture MUST follow a LOCAL-FIRST / PEER-TO-PEER model.
   184→
   185→Message content must never be stored on a central backend.
   186→
   187→Preferred architecture:
   188→
   189→CLIENT
   190→    |
   191→    +-- Local encrypted identity vault
   192→    |
   193→    +-- Local encrypted message database
   194→    |
   195→    +-- WebCrypto / mature cryptographic library
   196→    |
   197→    +-- WebRTC DataChannel
   198→    |
   199→    +-- Minimal signaling / rendezvous mechanism
   200→    |
   201→    +-- Optional STUN/TURN infrastructure
   202→    |
   203→    +-- Remote peer
   204→
   205→IMPORTANT:
   206→
   207→WebRTC requires signaling.
   208→
   209→Therefore do NOT falsely advertise:
   210→
   211→"100% backend-free"
   212→
   213→if signaling infrastructure is required.
   214→
   215→Instead architect the system so that:
   216→
   217→- signaling knows nothing about plaintext messages
   218→- signaling does not receive encryption keys
   219→- signaling does not receive message bodies
   220→- signaling cannot decrypt conversations
   221→- signaling does not store conversations
   222→- signaling only assists peers in finding each other / negotiating
   223→  connections
   224→- WebRTC carries the encrypted application payload
   225→
   226→If technically possible, make signaling ephemeral.
   227→
   228→Use short-lived signaling state.
   229→
   230→Delete signaling state after connection establishment.
   231→
   232→Do not build a permanent message database.

   237→
   238→This is the most important component.
   239→
   240→Use established cryptographic standards.
   241→
   242→DO NOT invent cryptography.
   243→
   244→The implementation should use a mature cryptographic library or
   245→well-reviewed browser-compatible primitives.
   246→
   247→Preferred direction:
   248→
   249→WebCrypto API for browser-native primitives where appropriate.
   250→
   251→Use modern authenticated encryption such as:
   252→
   253→AES-256-GCM
   254→
   255→or another well-established AEAD construction supported by the
   256→chosen cryptographic architecture.
   257→
   258→Use modern public-key cryptography for identity and key agreement.
   259→
   260→Where appropriate, use:
   261→
   262→X25519
   263→
   264→Ed25519
   265→
   266→HKDF
   267→
   268→SHA-256 / SHA-512
   269→
   270→AES-256-GCM
   271→
   272→or a mature protocol/library providing equivalent modern primitives.
   273→
   274→DO NOT simply implement a homemade "AES + RSA" chat protocol.
   275→
   276→DO NOT use insecure ECB mode.
   277→
   278→DO NOT reuse nonces.
   279→
   280→DO NOT derive keys using raw passwords directly.
   281→
   282→Use a proper password-based key derivation function for local vault
   283→protection, such as Argon2id where available through a trustworthy
   284→implementation.
   285→
   286→Use strong random values from:
   287→
   288→crypto.getRandomValues()
   289→
   290→or equivalent secure randomness.
